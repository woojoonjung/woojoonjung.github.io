# 프로젝트 이미지·영상 최적화 계획과 가이드

기준일: 2026-09-15. 현재 로컬 파일과 HTML/CSS를 확인해 작성한 실행 계획이다. 아래 목표 용량은 실제 변환 결과가 아니라 화질 비교를 시작하기 위한 작업 기준이다. 이 문서를 작성하면서 애셋이나 웹사이트 코드를 변경하지 않았다.

실행 기록: 이후 사용자 요청에 따라 프로젝트 이미지·영상 최적화를 완료했다. 실제 적용값과 검증 결과는 [프로젝트 애셋 최적화 결과](project-asset-optimization-results.md)에 기록했다. 아래 내용은 작업 전 계획과 일반 가이드다.

## 1. 확정한 범위와 원칙

- 대상: Bianca, Silverlining, Dr.Snap 등 프로젝트 상세 페이지에서 사용하는 사진, 렌더링, 도표 이미지, 영상, 영상 썸네일. 프로젝트 대표 이미지도 필요할 때만 포함한다.
- **로봇 애니메이션은 최적화하지 않는다.** `robot_and_woojun.png`는 포맷, 프레임, 크기, 파일 내용, 사용 방식 모두 그대로 유지한다.
- 프로필 사진, 연구 페이지 이미지, 로고, 폰트, CV는 이번 범위에서 제외한다.
- 프로젝트의 내용, 색감, 이미지 구도, 레이아웃과 영상의 의미를 보존한다. 읽을 수 있는 글씨나 중요한 디테일을 희생해 목표 용량을 맞추지 않는다.
- GitHub Pages를 유지한다. 외부 미디어 저장소 도입과 사이트 이전은 이번 작업에 포함하지 않는다.
- 원본을 먼저 별도 백업하고 웹용 사본을 만든다. 원본을 덮어쓰거나 이미 압축한 파일을 반복해서 재압축하지 않는다.

## 2. 현재 상태와 우선순위

프로젝트 폴더는 약 **152.17MiB**다. `.DS_Store`를 제외한 46개 파일 기준이며, 실제 방문자가 한 번에 다운로드하는 양과는 다르다. MiB는 파일 크기 단위이며 1MiB는 약 1.05MB다.

| 구성 | 파일 수 | 현재 용량 |
|---|---:|---:|
| MP4 영상 | 7 | 102.15MiB |
| PNG 이미지 | 29 | 44.21MiB |
| MOV 영상 | 4 | 5.67MiB |
| WebP 썸네일 | 4 | 0.13MiB |
| SVG | 2 | 0.01MiB 미만 |

| 우선순위 | 대상 | 현재 상태 | 처리 방향 |
|---|---|---|---|
| 1 | Bianca 데모 | 67.88MiB / 약 60초 / 720p | 원래 720p를 유지하고 영상 압축 설정 조정 |
| 1 | Silverlining 데모 | 22.64MiB / 약 18초 / 1080p | 1080p에서 압축 비교, 빠른 시작 설정 |
| 1 | 센서 실험 영상 | 5.96MiB / 약 4초 / 1080p | 720p 시안 비교, 필요 없는 오디오 제외, 화면 근처에서 재생 |
| 1 | Silverlining 본문 이미지 | 페이지에서 참조하는 이미지 합계 약 24.34MiB | 큰 PNG부터 WebP 및 적절한 크기로 변환 |
| 1 | Dr.Snap 인물 이미지 | `user_3_mother.png` 한 장이 5.19MiB | 카드에서 표시하는 크기에 맞춰 축소·변환 |
| 2 | Bianca·Dr.Snap 나머지 본문 이미지 | 각 페이지 이미지 합계 약 7.68 / 12.29MiB | 사진과 글씨 있는 도표를 구분해 처리 |
| 2 | Dr.Snap MOV 4개 | 같은 이름의 MP4도 존재 | MP4 검증 및 다운로드 링크 변경 후 MOV는 원본 보관 위치로 분리 |
| 3 | 이미 작은 대표 이미지·썸네일·SVG | 절감 효과가 상대적으로 작음 | 문제가 없으면 유지 |

페이지별 이미지 합계에는 대표 이미지와 영상 썸네일이 포함된다. 지연 로딩으로 인해 첫 화면에서 전부 내려받지는 않는다. Dr.Snap 영상은 이미 `preload="none"`과 썸네일을 사용하고 있어 이 동작을 유지한다.

## 3. 처음에 알아두면 되는 용어

| 용어 | 의미 | 이번 작업에서의 판단 |
|---|---|---|
| 해상도 | 이미지·영상의 가로와 세로 픽셀 수 | 실제 표시 크기보다 지나치게 큰 파일을 줄인다. 작은 원본을 확대하지 않는다. |
| 손실 압축 | 덜 눈에 띄는 정보를 줄여 파일을 가볍게 만드는 방식 | 사진과 영상에 사용하고 결과를 눈으로 비교한다. |
| 무손실 압축 | 디코딩된 픽셀을 보존하면서 압축하는 방식 | 작은 글씨, 선, 도표에서 우선 비교할 수 있다. 별도의 크기 축소는 픽셀을 바꾸므로 구분한다. |
| WebP | 웹에서 사용하는 이미지 형식 | 정지 이미지의 기본 출력 형식으로 사용한다. |
| H.264 / MP4 | 각각 영상 압축 방식 / 영상 파일을 담는 형식 | 이번 영상의 기본 조합이다. 확장자만 바꾸는 것은 압축이 아니다. |
| 지연 로딩 | 필요해질 때 다운로드를 시작하는 것 | 본문 아래 이미지, 화면 밖의 영상에 적용한다. |
| 썸네일 또는 poster | 영상을 재생하기 전에 보여주는 정지 이미지 | 사용자가 재생 전에 영상 내용을 알 수 있게 한다. |

## 4. 원본 보관과 파일 관리

1. 현재 프로젝트 파일의 목록, 용량, 해상도와 HTML에서 사용하는 경로를 기록한다.
2. 프로젝트 저장소 바깥의 별도 폴더에 원본을 **복사**한다. 예를 들어 Dropbox 안에 프로젝트 원본 전용 폴더를 만들고, 프로젝트별로 나눈다.
3. 복사한 파일의 개수와 파일 해시를 비교해 백업이 원본과 일치하는지 확인한다.
4. 웹용 사본은 새 이름으로 생성한다. 예: `silverlining_act-960.webp`, `silverlining_act-1600.webp`, `bianca_demo-web.mp4`.
5. HTML의 이미지·영상 경로와 원본 보기·다운로드 링크를 함께 변경한다.
6. 화면과 링크 검증을 마친 다음, 웹에서 더 이상 쓰지 않는 원본을 배포 대상에서 제외한다. 원본 백업은 유지한다.

실제 공개 파일은 기존 프로젝트별 `assets/projects` 하위 폴더에서 관리한다. 생성된 웹용 파일을 Git에 포함하면 GitHub Pages가 별도의 변환 도구 없이 그대로 제공할 수 있다.

주의할 점:

- 확장자가 PNG, MP4라는 이유로 전체를 `.gitignore`에 넣지 않는다. 필요한 공개 파일까지 빠지면 페이지가 깨진다.
- MOV는 현재 Dr.Snap의 대체 다운로드 링크에서도 사용된다. 먼저 MP4 재생을 확인하고 링크를 바꿔야 제외할 수 있다.
- HTML에서 참조되지 않는 것만으로 불필요하다고 단정하지 않는다. CSS, JavaScript와 직접 다운로드 링크도 확인한다.
- 이미 커밋한 파일에는 `.gitignore`만 추가해도 과거 Git 기록이 남는다. 기록 정리는 별도 작업이며 이 최적화 계획에는 포함하지 않는다.
- 미래에 다시 만들 때를 위해 입력 파일, 출력 파일, 픽셀 크기, 품질 설정, 전후 용량을 기록한다.

## 5. 이미지 설정 기준

첫 작업은 WebP 한 가지 형식으로 시작한다. AVIF나 여러 대체 포맷은 WebP 결과를 확인한 뒤 필요할 때 추가한다.

| 이미지 종류 | 크기 후보 | 품질 출발점 | 대략적인 파일 예산 |
|---|---|---|---|
| 작은 카드·인물 이미지 | 가로 480 / 800px | WebP 품질 80 | 50~200KB |
| 일반 본문 사진·렌더링 | 가로 960 / 1600px | WebP 품질 80 | 150~500KB |
| 넓은 화면에서 디테일이 중요한 이미지 | 가로 1600px부터 비교, 필요 시 2400px | WebP 품질 85 | 300~800KB |
| 작은 글씨·설계도·여정 지도 | 원본 크기 또는 읽기에 충분한 크기 | 무손실 WebP/기존 PNG와 손실 WebP 85~90을 비교 | 1MB 안팎까지 예외 허용 |
| 영상 썸네일 | 가로 640 / 1280px, 원본 비율 유지 | WebP 품질 75~80 | 30~150KB |
| 작은 SVG·이미 충분히 작은 이미지 | 현행 | 현행 | 유지 가능 |

이 숫자는 반드시 맞춰야 하는 규칙이 아니다. 원본보다 용량이 커지거나 눈에 띄게 나빠지면 해당 변환을 채택하지 않는다. 특히 기존 여정 지도는 약 0.23MiB이므로 먼저 줄여야 할 대상이 아니다.

크기는 화면에 표시되는 폭과 화면의 선명도를 함께 고려한다. 예를 들어 화면에서 가로 400px로 표시되는 사진은 선명한 화면을 위해 800px 후보를 제공할 수 있다. 현재 프로젝트 본문 컨테이너는 최대 1248px이며 내부 여백도 있으므로, 모든 이미지에 원본 3000~4000px를 일괄 제공할 필요는 없다. 1600px로 부족한 넓은 도표는 더 큰 후보를 유지한다. [반응형 이미지 원리](https://web.dev/learn/images/descriptive)

**작은 원본을 1600px로 확대하지 않는다.** 681px짜리 대표 이미지는 원본 범위 안에서 처리한다. 후보들은 같은 구도와 가로세로 비율을 유지한다. 색 공간은 웹 표시를 고려해 sRGB를 기본으로 하되, 변환 전후 색감을 비교하고 투명 배경은 보존한다.

### 직접 해보는 이미지 변환 순서

사용 도구: [Squoosh](https://squoosh.app/). 브라우저에서 미리보기를 비교하며 이미지 크기와 압축을 조정할 수 있다. [공식 프로젝트 안내](https://github.com/GoogleChromeLabs/squoosh)

1. 원본 이미지 사본 한 장을 연다.
2. Resize에서 필요한 가로 크기를 입력하고 가로세로 비율을 유지한다.
3. 출력 형식을 WebP로 선택하고 Quality 80에서 시작한다.
4. 비교 화면에서 얼굴, 제품 경계, 어두운 부분, 색의 경계, 글씨를 확인한다.
5. 차이가 잘 보이지 않으면 75를 비교한다. 글씨·경계가 뭉개지면 85 또는 90으로 올린다.
6. 새 파일명으로 다운로드하고 변환 전후 용량과 설정을 기록한다.
7. 같은 원본에서 다른 크기 후보를 만든다. 이미 축소·압축한 출력물을 다시 원본으로 사용하지 않는다.
8. 최종 판단은 도구의 확대 화면뿐 아니라 실제 페이지에서 표시되는 크기에서도 한다.

WebP의 품질 80은 원본 화질의 80%라는 뜻이 아니다. 다른 형식이나 다른 도구의 품질 숫자와도 직접 비교하지 않는다. 글씨와 선이 많은 그림은 사진과 다른 압축 설정이 필요할 수 있다. [WebP 설명](https://web.dev/learn/images/webp)

## 6. 영상 설정 기준

사용 도구: [HandBrake](https://handbrake.fr/). 아래 값은 **H.264 (x264)** 기준이다. 하드웨어 인코더나 다른 코덱에는 같은 품질 숫자를 그대로 적용하지 않는다.

| 설정 | 기본값 또는 선택 기준 |
|---|---|
| Format | MP4 |
| Web Optimized | 켜기. 재생 정보를 파일 앞쪽에 배치한다. |
| Video Encoder | H.264 (x264) |
| Quality | Constant Quality, RF 22부터 비교 |
| Encoder Preset | Medium부터 시작. 필요하면 Slow의 용량·처리시간 비교 |
| Dimensions | 원본 비율 유지, 확대 금지, 의도하지 않은 자동 잘라내기 해제 |
| Framerate | 원본이 30fps 이하이면 유지. 초과할 때만 30fps 시안을 비교하고 움직임이 중요하면 원본 유지 |
| Audio | 의미 있는 음성·음악은 유지. 음질 비교가 필요하면 AAC 128kbps를 출발점으로 사용 |
| 무음 반복 영상 | 오디오가 불필요한 것으로 확인된 경우 오디오 트랙 제외 |

RF는 **숫자가 낮을수록 높은 품질·큰 용량**을 지향한다. RF 22에서 글씨나 움직임이 깨지면 21, 20으로 내려 비교한다. 용량이 더 필요하면 한 단계 올려 비교한다. 결과 크기를 고정하지 않는 방식이므로 같은 설정이어도 영상마다 용량이 다르다.

HandBrake의 공식 권장 범위는 x264 기준 720p에서 RF 19~23, 1080p에서 RF 20~24다. 이 가이드는 그 범위 안의 RF 22를 첫 비교값으로 선택했다. 이는 모든 영상의 최적값이라는 뜻은 아니다. [HandBrake 품질 설정 안내](https://handbrake.fr/docs/en/latest/workflow/adjust-quality.html)

| 파일 | 첫 시안 | 작업 목표 용량 | 합격 기준 |
|---|---|---|---|
| Bianca 데모 | 원본 1280×720 유지, RF 22 | 약 15~25MiB | 조명 변화, 어두운 장면, 손 동작, 음악·음성 보존 |
| Silverlining 데모 | 원본 1920×1080 유지, RF 22 | 약 4~8MiB | 빛의 계조, 제품 표면과 이동 모습 보존 |
| 센서 실험 | 1280×720 시안, RF 22 | 약 0.5~1.5MiB | 센서 반응과 실험 동작을 분명히 볼 수 있음 |
| Dr.Snap MP4 4개 | 현행을 먼저 유지하고 필요할 때만 비교 | 현재 합계 약 5.67MiB를 기준으로 판단 | UI 글씨, 커서, 응답 내용이 읽히고 탐색·재생이 정상 |

위 크기는 변환 전 가설이다. 실사 영상보다 화면 녹화에서는 작은 글씨가 더 중요하므로 Dr.Snap 영상을 무조건 720p나 16:9로 바꾸지 않는다. 원래 비율을 유지하고 글씨가 읽히는 해상도를 택한다.

Web Optimized는 시작을 돕는 파일 배치 설정이며 영상 화질을 자동으로 조절하거나 영상 자체를 압축하는 기능은 아니다. Bianca는 현재 재생 정보가 앞에 있고, 센서 실험과 Silverlining 영상은 뒤에 있어 후자의 두 파일에 특히 적용할 이유가 있다. [FFmpeg의 빠른 시작 설명](https://ffmpeg.org/ffmpeg-formats.html#Fragmentation)

### 직접 해보는 영상 변환 순서

1. 원본 영상 사본을 HandBrake에서 연다.
2. MP4와 Web Optimized를 선택한다.
3. 영상 크기, 가로세로 비율, 잘라내기 값을 확인한다.
4. H.264 (x264), Constant Quality RF 22, Medium을 선택한다.
5. 프레임 수와 오디오를 확인하고 새 이름으로 저장한다.
6. 원본과 결과의 같은 시점을 나란히 비교한다. 시작·중간·끝뿐 아니라 가장 어두운 장면, 움직임이 큰 장면, 작은 글씨가 있는 장면을 확인한다.
7. 화질이 부족하면 RF를 낮추고, 용량이 너무 크면 한 단계 높여 다시 원본에서 출력한다.
8. Safari와 Chrome에서 재생, 소리, 영상 중간으로 이동, 모바일 전체 화면을 확인한다.

## 7. 페이지에서 불러오는 규칙

파일을 줄이는 작업과 다운로드를 늦추는 작업을 함께 한다.

| 위치·종류 | 적용할 동작 |
|---|---|
| 프로젝트 첫 화면의 대표 이미지 | 바로 로딩한다. 첫 화면 핵심 이미지에는 지연 로딩을 넣지 않는다. |
| 본문 아래 이미지 | `loading="lazy"`, 실제 비율에 맞는 `width`·`height`, 필요한 크기의 후보 제공 |
| 크기 후보가 여러 개인 이미지 | `srcset`과 실제 레이아웃에 맞는 `sizes`를 함께 설정 |
| 사용자가 재생하는 데모 | 가벼운 썸네일과 재생 컨트롤을 먼저 표시, `preload="none"` 사용 |
| 재생 전 영상 다운로드를 확실히 막아야 하는 경우 | 재생 동작 전에는 영상 소스를 연결하지 않고, 재생 버튼을 누를 때 연결 |
| 센서 실험 자동 재생 | 화면 가까이에 왔을 때 소스를 연결·재생하고, 화면을 벗어나면 일시 정지 |
| 동작 줄이기 설정을 사용하는 방문자 | 센서 실험도 썸네일과 수동 재생 제공 |

`preload`는 브라우저에 주는 힌트다. 실제로 재생 전 데이터를 받는지는 Network 탭에서 확인해야 한다. 자동 재생 영상에 `preload="none"`만 추가해도 다운로드가 방지된다고 가정하지 않는다. [영상 지연 로딩 안내](https://web.dev/articles/lazy-loading-video), [MDN의 preload 설명](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video#preload)

재생 버튼은 마우스뿐 아니라 키보드와 터치로도 사용할 수 있어야 한다. 재생 실패 시 대체 링크를 제공하고, 영상이 페이지 밖에서 계속 재생되지 않게 한다. 자동 재생은 브라우저 정책에 따라 거절될 수 있으므로 수동 재생을 유지한다.

이 사이트는 페이지 안에서 다른 페이지로 이동할 때 내용을 교체하는 기능이 있으므로, 직접 주소로 들어오는 경우와 사이트 메뉴를 통해 이동하는 경우를 모두 확인한다. 프로젝트 영상 관련 이벤트와 관찰자는 페이지를 떠날 때 정리하고, 로봇 요소에는 적용하지 않는다.

## 8. 실제 실행 순서와 단계별 완료 조건

| 단계 | 하는 일 | 완료 조건 |
|---|---|---|
| 1. 기준 기록·백업 | 프로젝트 애셋 목록과 사용처 기록, 원본 복사와 검증 | 원본 복원이 가능하고 제외 대상이 명확함 |
| 2. 대표 시안 | Silverlining 렌더링, Dr.Snap 인물 사진, 글씨 있는 도표, Bianca 영상으로 시안 제작 | 실제 페이지 크기에서 화질·색감·가독성 검증 |
| 3. 이미지 적용 | 시안에서 확정한 설정으로 나머지 정지 이미지 처리, 경로와 크기 후보 연결 | 깨진 이미지가 없고 모바일에 불필요하게 큰 파일을 주지 않음 |
| 4. 영상 적용 | 큰 영상 3개 압축, 썸네일·빠른 시작 설정, Dr.Snap 현행 검증 | 재생·소리·탐색이 정상이고 중요한 디테일 보존 |
| 5. 로딩 동작 | 본문 지연 로딩, 데모 수동 재생, 센서 실험 화면 근처 재생 | 사용자 동작 전후의 실제 네트워크 요청이 의도와 일치 |
| 6. 원본 분리·정리 | 사용 중인 모든 링크 변경 확인 후 불필요한 원본 배포 제외 | MOV 등 대체 링크가 깨지지 않고 백업이 유지됨 |
| 7. 배포 전 확인 | PC·모바일, 직접 방문·페이지 이동, 콜드로드 비교 | 아래 품질·기능 기준을 충족하고 결과 기록 |

처음부터 모든 파일을 같은 설정으로 일괄 변환하지 않는다. 대표 시안에서 설정을 확정한 후 유사한 유형끼리 적용한다. 프로젝트별로 교체·검증하면 문제 발생 시 그 프로젝트만 되돌릴 수 있다.

## 9. 성능 목표와 확인 방법

### 작업 예산

- 프로젝트 웹용 파일 전체는 우선 **60MiB 이하**를 검토 목표로 둔다. 모바일·데스크톱 후보를 모두 합친 배포 파일 용량 기준이다. 화질이 부족하면 목표를 완화한다.
- 동영상을 재생하지 않은 첫 화면은 **전송량 약 2MB 이하**를 목표로 비교한다. HTML·CSS·JavaScript·폰트·이미지 등 해당 페이지가 실제로 받은 파일을 포함한다.
- 첫 화면 핵심 이미지는 가능하면 300KB 이내에서 시작한다.
- 1MB를 넘는 본문 이미지와 10MiB를 넘는 영상은 변환 실패로 간주하지 않고, 화질상 필요한 이유를 한 번 더 확인한다.
- 목표 용량을 달성했어도 중요한 글씨·색감·영상 내용이 나빠졌으면 채택하지 않는다.

### 같은 조건으로 전후 비교

1. 같은 브라우저와 컴퓨터에서 비교하고 버전을 기록한다.
2. 브라우저 개발자 도구의 Network에서 캐시를 끈다. 단순 새로고침으로 캐시된 결과를 비교하지 않는다.
3. 모바일은 예를 들어 390×844, 데스크톱은 1440×900으로 고정한다. 화면의 픽셀 밀도 설정도 전후 동일하게 둔다.
4. 모바일 회선 시뮬레이션은 같은 프로필을 계속 쓴다. 필요하면 다운로드 4Mbps, 지연 150ms 같은 고정 조건을 만든다. 이 설정은 보편적인 실제 모바일 속도를 뜻하지 않는다.
5. 페이지를 새로 열고 10초간 스크롤·재생하지 않은 상태의 전송량을 기록한다. 이어서 끝까지 스크롤하고, 영상을 각각 재생해 요청이 발생하는 시점을 따로 확인한다.
6. 같은 조건에서 3회 확인하고 대표값으로 중앙값을 기록한다. 사이트 내부 이동도 별도로 확인한다.
7. Lighthouse의 모바일 보고서로 큰 이미지, 화면 밀림, 첫 화면 핵심 콘텐츠 표시 지연을 살펴본다. 단일 점수만으로 완료를 판단하지 않는다.

### 반드시 통과할 품질·기능 체크리스트

- [ ] 모든 원본의 별도 백업이 확인되었다.
- [ ] 로봇 파일과 로봇의 표시·애니메이션 동작이 변경되지 않았다.
- [ ] 프로젝트 외 애셋이 변경되지 않았다.
- [ ] 작은 글씨, 제품 윤곽, 빛의 계조와 색감이 허용 가능한 수준으로 보존되었다.
- [ ] 이미지가 찌그러지거나 예상과 다르게 잘리지 않는다.
- [ ] 이미지가 나타날 때 본문이 갑자기 밀리지 않는다. 파일 비율과 HTML 속성도 확인했다.
- [ ] 첫 화면 대표 이미지가 지연 로딩 때문에 늦어지지 않는다.
- [ ] 모바일에 적절한 크기의 이미지 후보가 선택된다.
- [ ] 수동 재생 영상이 재생 전에 불필요하게 다운로드되지 않는다.
- [ ] 센서 실험 영상은 의도한 시점에 시작하며 수동 재생도 가능하다.
- [ ] 영상 재생·탐색·소리·모바일 전체 화면이 정상이다.
- [ ] 프로젝트 사이를 이동하거나 뒤로 가도 재생과 지연 로딩이 동작한다.
- [ ] 원본 보기·영상 다운로드·대체 링크에서 404가 발생하지 않는다.
- [ ] Safari와 Chrome, 실제 휴대전화에서 확인했다.
- [ ] 전후 파일 용량과 페이지 전송량을 서로 구분해 기록했다.
- [ ] 위 확인 후에만 배포할 파일을 커밋 대상으로 선택했다.

## 10. 이후 프로젝트를 추가할 때의 반복 규칙

새 프로젝트에서는 `원본 보관 → 사용 위치 결정 → 대표 시안 → 웹용 출력 → 페이지 연결 → 모바일 확인` 순서로 반복한다. 작업 기록에는 원본 경로, 출력 파일명, 크기·품질 설정, 전후 용량과 검증 결과를 남긴다.

영상이 길어지거나 수가 많아져도 방문자가 재생하지 않은 영상을 자동으로 모두 받게 하지 않는다. 최적화 후에도 영상 관리나 방문 트래픽이 부담이 되는 시점에 외부 영상 저장소를 별도로 검토한다.
